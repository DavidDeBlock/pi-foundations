# Issue Readiness Check

## Reference docs

- [.pi/ISSUE-INTERACTION.md](../../.pi/ISSUE-INTERACTION.md) — label, comment, and body-edit conventions for multi-agent flows

---

## Quick start
1. Fetch the issue using `gh issue view <number>`.
2. Evaluate against 5 key dimensions: Goal, Acceptance Criteria, Scope Boundaries, Domain Context, Implementation Hints, Test Expectations.
3. Output a structured report indicating readiness status and specific gaps.

---

## Workflow: Self-Containment Audit

### 0. Read Previous Handoffs
Before auditing, fetch all comments and scan for `🤖 Agent Handoff:` prefix.
Parse JSON blocks from matching comments to understand what previous agents found.
Use this as context — still make your own verdict.

```bash
gh issue view <number> --json title,body,labels,comments
```

---

Run the following checklist against the issue body. Be strict—if a builder can't answer "What?" or "Where?", flag it.

### 1. Goal Summary (The "Why")
*   **Check**: Is there a clear problem statement? Does it link to relevant docs (`CONTEXT.md`, `WORLD.md`) or define specific domain terms (e.g., "Settlement", "Void")?
*   **Fail**: Vague goals ("Fix the login"), undefined jargon, no links.

### 2. Acceptance Criteria (The "What")
*   **Check**: Are ACs specific and testable? Look for checkboxes or clear bullet points describing expected behavior (e.g., "Returns 401 on invalid token").
*   **Fail**: Missing ACs, vague language ("Make it faster"), subjective terms ("User-friendly").

### 3. Scope Boundaries (The "What Not")
*   **Check**: Does the issue explicitly state what is *out of scope*? This prevents builder over-engineering.
*   **Fail**: No explicit exclusion list or boundary definition.

### 4. Implementation Hints (The "Where")
*   **Check**: Are specific file paths, DB tables, or API endpoints mentioned? (e.g., "Update `server/src/routes/auth.ts`", "Add column to `users` table").
*   **Fail**: Generic instructions ("Fix the backend"), forcing the builder to guess location.

### 5. Test Expectations (The "Proof")
*   **Check**: Does it mention required test scenarios? (e.g., "Unit test for error handling", "Integration test for API endpoint").
*   **Fail**: No mention of testing or verification steps.

## Structured Output & Comment

After the audit, post a structured comment on the issue following the format in [.pi/ISSUE-INTERACTION.md](../../.pi/ISSUE-INTERACTION.md) §2.

### Readiness Report (in comment body)
| Dimension | Status | Detail |
|-----------|--------|--------|
| Goal Summary | ✅ Pass / ❌ Fail | [Reason] |
| Acceptance Criteria | ... | ... |
| Scope Boundaries | ... | ... |
| Implementation Hints | ... | ... |
| Test Expectations | ... | ... |

**Verdict**: `READY` (All critical dims pass) or `BLOCKED` (Critical gaps found).

### JSON Verdict Format
Include this JSON block inside the comment's `<details>` section:

```json
{
  "agent": "issue-readiness",
  "flow": "self-containment-audit",
  "verdict": "ready" | "blocked",
  "score": <0-100>,
  "labels": {
    "add": ["ready-for-agent"],
    "remove": []
  },
  "gaps": [
    {
      "dimension": "<name>",
      "severity": "critical" | "warning",
      "detail": "<specific missing piece>"
    }
  ]
}
```

### Label Rules by Verdict
| Verdict | Add Labels | Remove Labels |
|---------|-----------|---------------|
| `READY` | `ready-for-agent` | `needs-info`, `status:blocked` |
| `BLOCKED` | `needs-info` | `ready-for-agent` |

### Posting the Comment
```bash
gh issue comment <number> --body "$(cat <<'EOF'
## 🤖 Agent Handoff: `issue-readiness`

> *This was generated by AI during readiness check.*

### Summary
[One-line summary of audit result]

### Findings / Advice
- [Finding 1]
- [Finding 2]

---
<details><summary>Structured Data</summary>

```json
{ ... verdict JSON ... }
```

</details>
EOF
)"
```

Then apply label changes:
```bash
gh issue edit <number> --add-label "label1" --remove-label "label2"
```

---

## Guardrails
*   **Do not rewrite the issue.** Only audit and verify.
*   If a dimension is vague, flag it as `needs_clarification` rather than failing outright (unless critical).
*   Assume the builder has **zero** prior context—every term must be explained or linked.

## Handoff
| To | When |
|----|------|
| `typescript-implementer` | Issue is `READY` and assigned to a builder (verdict: `ready`) |
| `archivist` | Blocked due to missing codebase context — Archivist should enrich issue body |
| `to-prd` | Issue is `BLOCKED`, needs restructuring before assignment |
| `finish` | Audit complete, comment posted, labels applied |

**Label changes are applied immediately after posting the comment.** See [.pi/ISSUE-INTERACTION.md](../../.pi/ISSUE-INTERACTION.md) §1 for details.
