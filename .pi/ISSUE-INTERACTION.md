# Issue Interaction Contract

**Purpose:** Defines how agents read from and write to GitHub issues during multi-agent flows. All skills that interact with issues must follow these conventions.

**Authority:** [ADR-009](../docs/40-decisions/ADR-009-issue-interaction-contract.md)

---

## Unified Verdict Format (Dual Consumer)

Every agent emits **one JSON verdict block** that serves two consumers:

| Field | Consumed By | Purpose |
|-------|-------------|---------|
| `status` (`approved`/`rejected`) | **Maestro Pipeline** (`verdict_extractor.py`) | Controls phase transitions (continue/stop/retry) |
| `verdict` (e.g., `ready`, `blocked`, `enriched`) | **Agents** reading GitHub issues | Semantic meaning for handoff decisions |
| `labels` (`{add, remove}`) | **Agents** applying label changes | Deterministic issue state management |
| `findings` (array) | **Agents** building on previous work | Structured context for next phase |
| `details`, `issues` | **Both** | Shared metadata |

### Example Unified Verdict
```json
{
  "status": "approved",
  "verdict": "ready",
  "details": "All ACs verified and self-contained",
  "issues": [],
  "labels": {
    "add": ["ready-for-agent"],
    "remove": ["needs-info", "status:blocked"]
  },
  "findings": []
}
```

**Rules:**
- `verdict_extractor.py` only reads `status` — extra fields are ignored (safe to add)
- Agents reading GitHub issues parse the full JSON including `labels`, `verdict`, and `findings`
- All templates in `.pi/maestro/prompts/` use this unified format
- Skills reference this contract rather than defining their own verdict shapes

## 1. Verdict-Driven Labels

Every skill's JSON verdict **must** include a `labels` field specifying what to add and remove:

```json
{
  "verdict": "<approved|rejected|enriched>",
  "reasons": ["..."],
  "labels": {
    "add": ["label-to-add"],
    "remove": ["label-to-remove"]
  }
}
```

The consuming agent executes:
```bash
gh issue edit <number> --add-label "label1,label2" --remove-label "label3"
```

**Empty arrays are valid** — if no label change is needed, use `"labels": { "add": [], "remove": [] }`.

## 2. Structured Comment Format

All agent handoff comments **must** follow this exact template:

```markdown
## 🤖 Agent Handoff: `<skill-name>`

> *This was generated by AI during [flow name].*

### Summary
One-line summary of what this agent did and found.

### Findings / Advice
- Point 1
- Point 2

---
<details><summary>Structured Data</summary>

```json
{
  "agent": "<skill-name>",
  "flow": "<flow-name>",
  "verdict": "<approved|rejected|enriched>",
  "labels": { "add": [], "remove": [] },
  "findings": [ ... ]
}
```

</details>
```

**Rules:**
- The `🤖 Agent Handoff:` prefix is mandatory — it enables discovery (see §4)
- The JSON block must be valid and match the prose content
- Use `<details>` tags to keep JSON collapsible in GitHub rendering

## 3. Body Edits: Archivist Only

| Agent | Can Edit Body? | Mechanism |
|-------|---------------|-----------|
| **Archivist** | ✅ Yes | Within `<!-- AGENT-FINDINGS-START/END -->` markers |
| All others | ❌ No | Comments only |

### Archivist Body Edit Rules

1. Search for existing `<!-- AGENT-FINDINGS-END -->` marker
2. If found, insert new findings **before** it (append within the section)
3. If not found, append both markers and the new content at the end of the body:

```markdown
<!-- AGENT-FINDINGS-START -->
## Agent Findings

### Archivist — YYYY-MM-DD
- Finding 1 based on codebase exploration
- Finding 2 with file references
<!-- AGENT-FINDINGS-END -->
```

4. Never edit content outside these markers
5. Always post a structured comment (see §2) alongside the body edit

---

## 4. Comment Discovery Prefix

Agents identify machine-readable handoff comments by scanning for:

```
🤖 Agent Handoff: <skill-name>
```

**Rules:**
- Every agent handoff comment **must** start with this prefix
- Human comments without this prefix are ignored during structured parsing
- The `<skill-name>` must match the skill's identifier (e.g., `prd-auditor`, `issue-readiness`, `archivist`)

---

## 5. Always Read Previous Handoffs

Before acting on an issue, agents **must**:

1. Fetch all comments: `gh issue view <number> --comments`
2. Scan for `🤖 Agent Handoff:` prefix in each comment body
3. Parse the JSON block from matching comments
4. Use findings as **context** (not authority) — still make your own verdict

This prevents:
- Circular rejection loops (same reasons repeated)
- Duplicate codebase searches
- Asking questions already answered by previous agents

---

## 6. Re-Review Trigger

After Archivist enriches an issue body, it signals readiness for re-review via labels in its verdict:

```json
{
  "agent": "archivist",
  "verdict": "enriched",
  "labels": {
    "add": ["ready-for-agent"],
    "remove": ["needs-info"]
  }
}
```

This label change signals the pipeline (or maintainer) that the issue is ready for another review pass. The Archivist does **not** re-run Issue Readiness itself — it only drives the transition via labels.

---

## 7. Reference Commands

### Reading an Issue with Comments and Labels
```bash
gh issue view <number> --json title,body,labels,comments --jq '{title: .title, body: .body, labels: [.labels[].name], comments: [.comments[] | {user: .author.login, body: .body}]}'
```

### Applying Label Changes from Verdict
```bash
# Add labels
gh issue edit <number> --add-label "needs-info,status:blocked"

# Remove labels  
gh issue edit <number> --remove-label "ready-for-agent"

# Both simultaneously
gh issue edit <number> --add-label "needs-info" --remove-label "ready-for-agent"
```

### Posting a Comment
```bash
gh issue comment <number> --body "$(cat <<'EOF'
## 🤖 Agent Handoff: `skill-name`
...content...
EOF
)"
```
